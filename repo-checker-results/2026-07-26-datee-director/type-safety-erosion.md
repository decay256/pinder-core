### Finding 1: Complete prompt entries still require nullable suppressions at the director boundary
**File**: `src/Pinder.LlmAdapters/PinderLlmAdapter.EmotionalDirector.cs:30`; `src/Pinder.LlmAdapters/EmotionalReactionPromptCatalog.cs:217`
**Issue**: The #1341 director path calls `catalog.RequireCompleteEntry(...)`, but the returned type is still the nullable-field `PromptEntry`, so production code has to silence nullable analysis with `prompt.UserTemplate!`, `prompt.SystemPrompt!`, and `entry.UserTemplate!` before sending or validating the prompt. The context API at `src/Pinder.LlmAdapters/PromptCatalog.cs:222` proves completeness only by throwing; it does not return a type whose `SystemPrompt`, `UserTemplate`, `Temperature`, and `MaxTokens` are non-null.
**Impact**: The prompt/catalog boundary remains stringly and nullable even after runtime validation. Future director or prompt-catalog call sites can accidentally reuse a `PromptEntry` path that has not gone through completeness validation, and the compiler cannot distinguish a complete runtime prompt from a partial prompt entry once `!` has spread to consumers.
**Urgency**: U3 - topic default; this is maintainability/type-contract erosion on an internal LLM prompt boundary, not an observed production failure.
**Fixer-Agent Action Plan**: Introduce a non-null complete-entry return shape, such as `CompletePromptEntry` or a `RequireCompletePrompt(...)` method returning non-null system prompt, user template, temperature, and max-token values. Update `PinderLlmAdapter.GenerateEmotionalDirectionAsync` and `EmotionalReactionPromptCatalog.RequireCompletePromptWithPlaceholders` to consume that typed result and remove the nullable suppressions.
