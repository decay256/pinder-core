### Finding 1: Emotional director schema version is advertised out-of-band but not part of the payload contract
**File**: `src/Pinder.LlmAdapters/EmotionalDirectorContract.cs:42`; `src/Pinder.LlmAdapters/EmotionalDirectorContract.cs:374`; `tests/Pinder.LlmAdapters.Tests/Issue1341_EmotionalDirectorContractTests.cs:38`
**Issue**: The new contract declares `public const string SchemaVersion = "emotional_director.v1"` and the focused test asserts `transport.LastStructuredRequest.SchemaVersion`, but `BuildJsonSchema()` requires only `new JArray(Fields)` and `TryParse()` accepts only those seven data fields via `HasOnlyProperties(root, out var unexpected, Fields)`. A returned object cannot carry `"schema_version":"emotional_director.v1"` without being rejected as `unexpected_field`, unlike the existing `DialogueOptionsStructuredContract` pattern that requires and validates an in-payload `schema_version`.
**Impact**: Captured emotional-director JSON objects are not self-describing. If the director shape later migrates to v2, stored/replayed raw payloads, local fallback parsing, and provider transports cannot distinguish old v1 objects from new objects by inspecting the object itself; the schema version survives only in the request metadata path.
**Urgency**: U2 - de-escalated from the topic default U1 because this is a private, currently unwired LLM contract rather than persisted production database data, but it will bite the next contract migration.
**Fixer-Agent Action Plan**: Add a required `schema_version` string property with const `EmotionalDirectorContract.SchemaVersion` to the emotional director JSON schema, parser allow-list, and validation logic; update `data/prompts/emotional-reactions.yaml` to instruct the model to include it; add Issue1341 regressions for accepted matching schema versions and rejected missing/wrong schema versions.
