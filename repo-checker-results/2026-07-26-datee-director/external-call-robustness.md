### Finding 1: Native structured director responses bypass the existing JSON size guard
**File**: `src/Pinder.LlmAdapters/PinderLlmAdapter.EmotionalDirector.cs:66`; `src/Pinder.LlmAdapters/EmotionalDirectorContract.cs:181`
**Issue**: The new emotional-director call passes `structuredResponse.JsonText` into `ParseEmotionalDirectorOrThrow(... requireCompleteJsonObject: structuredResponse.UsedNativeStructuredOutput ...)`. When `UsedNativeStructuredOutput` is true, `EmotionalDirectorContract.TryParse` skips `GeneratedJsonObjectExtractor.TryExtractFirstValidObject(jsonText)` and only checks `string.IsNullOrWhiteSpace(json)` before `JToken.ReadFrom(jsonReader, ...)`. The plain and non-native structured paths therefore get the extractor's `DefaultMaxInputChars` / `DefaultMaxObjectChars` bounds, while the native structured path parses the provider-returned string with no local character/object bound before allocation.
**Impact**: A provider bug, proxy corruption, malicious test transport, or native structured-output regression can return an oversized object/string and force the adapter to allocate and parse it before the seven 180-character field limits run. That makes this new callable LLM operation less robust than the fallback path and can tie up memory/CPU during DATEE response generation instead of failing fast with a sanitized contract rejection.
**Urgency**: U1 - topic default because this is an unbounded response-handling gap on a new external LLM call path.
**Fixer-Agent Action Plan**: Add the same local size guard to the native structured branch before `JToken.ReadFrom`, either by routing through `GeneratedJsonObjectExtractor` with an option that requires a complete object or by adding an explicit `json.Length <= GeneratedJsonObjectExtractionOptions.DefaultMaxObjectChars` check with a stable rejection reason. Cover both oversized native `StructuredLlmResponse(... usedNativeStructuredOutput: true)` and oversized non-native/plain responses in `Issue1341_EmotionalDirectorContractTests`.
