### Finding 1: Director prompt validation duplicates the existing placeholder validator
**File**: `src/Pinder.LlmAdapters/EmotionalReactionPromptCatalog.cs:208`
**Issue**: The #1341 addition creates `RequireCompletePromptWithPlaceholders` and `RequirePlaceholderInTemplate`, but they repeat the same placeholder construction and missing-token exception pattern already present in `RequireSystemPromptWithPlaceholders` / `RequirePlaceholder` at `src/Pinder.LlmAdapters/EmotionalReactionPromptCatalog.cs:188`. The duplicated code is visible in `string placeholder = "{" + token + "}";` and the matching `template.IndexOf(placeholder, StringComparison.Ordinal) < 0` / `prompt.IndexOf(placeholder, StringComparison.Ordinal) < 0` checks.
**Impact**: Any future hardening of prompt-token validation, error wording, or source-field attribution now has to update two near-identical local helper paths. Because runtime catalog validation is the gate that keeps edited YAML from silently losing required tokens, drift here makes the next prompt-contract extension easier to validate differently by accident.
**Urgency**: U3 — topic default; this is maintainability drift in a validation helper, not an immediate behavior break.
**Fixer-Agent Action Plan**: Replace both placeholder-specific helpers with one helper that accepts the template text plus a field label (`system_prompt`, `user_template`), then have `RequireSystemPromptWithPlaceholders` and `RequireCompletePromptWithPlaceholders` call it. Prefer using or extending `PromptCatalog`'s runtime token-contract validation if that keeps prompt contract checks centralized.

### Finding 2: Mechanical shorthand lists copy the same stat and outcome tokens three times
**File**: `src/Pinder.LlmAdapters/EmotionalDirectorContract.cs:59`
**Issue**: `MechanicalShorthandValues` repeats every stat token from `MechanicalStatValues` (`"charm"`, `"rizz"`, `"honesty"`, `"chaos"`, `"wit"`, `"self-awareness"`, `"self_awareness"`) and every tier token from `MechanicalTierValues` (`"clean"`, `"strong"`, `"critical"`, `"exceptional"`, `"nat20"`, `"fumble"`, `"misfire"`, `"trope-trap"`, `"trope_trap"`, `"catastrophe"`, `"nat1"`). The same concepts already have canonical sources nearby: `StatType` / `StatNameNormalizer` for stats and `StatDeliveryInstructions.OutcomeTierKeys` via `EmotionalReactionPromptCatalog.OutcomeKeys` for outcome keys.
**Impact**: Adding, renaming, or normalizing a stat/outcome token requires editing multiple lists in lockstep. If one list is missed, the director can inconsistently reject a one-word shorthand while still accepting or rejecting the equivalent `stat tier` form, leaving the private contract validator weaker than its tests imply.
**Urgency**: U3 — topic default; the current values are internally consistent, but the duplicated catalog is brittle for future mechanics changes.
**Fixer-Agent Action Plan**: Build `MechanicalStatValues` from `Enum.GetValues(typeof(StatType))` plus existing wire-token normalization, build `MechanicalTierValues` from the existing outcome key list plus hyphen/underscore aliases, and derive `MechanicalShorthandValues` as a union with the relationship-state extras. Keep the rejection-matrix tests, but make them assert behavior rather than pinning the duplicate list.

### Finding 3: The seven-field director contract is copied across YAML, docs, and parser/schema code
**File**: `data/prompts/emotional-reactions.yaml:86`
**Issue**: The director prompt lists `primary_emotion, intensity, underlying_feeling, interpretation, impulse, restraint, response_posture`, while `src/Pinder.LlmAdapters/EmotionalDirectorContract.cs:48` independently defines the same `Fields` array and `docs/prompts.md:100` / `docs/modules/llm-adapters.md:78` copy the same list again. The runtime validator added in `src/Pinder.LlmAdapters/EmotionalReactionPromptCatalog.cs:167` only checks that `emotional-reaction-director.user_template` contains `{compiled_reaction_input}`; it does not verify that the YAML field instructions still match `EmotionalDirectorContract.Fields`.
**Impact**: A future prompt edit can rename, omit, or add a director field in YAML while the native structured schema and parser still require the old C# field list. Plain transports would then receive misleading instructions, and docs could continue to affirm a different contract than the runtime enforces.
**Urgency**: U3 — topic default; the current field lists match, but the duplication creates a prompt-contract drift hazard.
**Fixer-Agent Action Plan**: Expose the director field list through a single internal contract surface and validate the `emotional-reaction-director` prompt against it during `ValidateRuntimeCatalog`. If possible, render the field list into the prompt at call time or add a dedicated prompt-catalog contract that requires all `EmotionalDirectorContract.Fields` tokens to be present. Update docs to refer to the contract surface rather than maintaining another hand-copied list.
